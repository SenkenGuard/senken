# senken-indicator-compile

Compiles a user-submitted Rust indicator to a `wasm32-wasip2` component that
`senken-plugin-host` can load.

## What this crate is, and is not

It knows nothing about accounts, storage, or HTTP. Given a source string, it
either returns compiled bytes or a typed compile error with a line and
column. Everything about *whose* indicator this is, where the source and the
result are stored, and what endpoint exposes it belongs to the caller
(`senken-api`'s `user_indicator_handlers`), not here — the same separation
`senken-venue` keeps from every venue plugin that uses it.

## Why a real `cargo build`, and why that is safe here

The user's crate has exactly one dependency, `senken-plugin-api`, and no
`build.rs`: `cargo build` cannot run arbitrary third-party build scripts or
proc macros on this host, because there is nothing here to run one. The
`Cargo.toml` the user's crate builds with is generated by this crate on
every compile, never accepted from the caller, so it cannot smuggle in a
dependency of its own.

A handful of source forms are rejected before `cargo` ever runs
(`include_str!`, `include_bytes!`, `unsafe`, `std::fs`, `std::net`, and a
few others) — a rejection of *form*, not a security boundary. The boundary
that actually matters is the WASM sandbox the compiled component runs
inside once `senken-plugin-host` loads it; this crate's job is only to keep
someone from reading files off the build machine at *build* time, before
that sandbox exists.

## Concurrency and the target directory

Exactly one build runs at a time, behind an internal lock — this machine
must never run two Rust builds concurrently, and a compile service used by
more than one request at once is exactly how that would happen by accident.
`CARGO_TARGET_DIR` is fixed per [`CompileService`], so a second compile of
a different indicator still gets a warm dependency cache.
